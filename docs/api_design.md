# Prediction and recommendation API design

This is a **research prototype**. It scores the six CORE schemes with a hybrid documented-rule engine plus the saved Decision Tree, stores an academic socio-economic data wallet in PostgreSQL, and returns eligibility-based recommendations. It is not government approval and is not connected to any official Tamil Nadu API.

This authentication system is implemented for the academic research prototype. It is not a government identity verification system. Wallet routes require a JWT. Public `/predict`, `/recommend`, and `/evaluation` do not.

| Field | Meaning |
| --- | --- |
| `scheme_id` | Scheme that was scored |

| `agreement` | Whether the rule result and ML prediction match |

Probabilities are model outputs, not “eligibility certainty” and not government approval.

| Situation | Status |
| --- | --- |
| Valid request | 200 |
| Invalid age, negative land, invalid `scheme_id`, missing field, malformed JSON | 422 |
| Model artifact missing or not loaded | 503 |
| Unexpected server error (no stack trace in the body) | 500 |

## Processing steps

1. Validate the request body.
2. Convert fields to the feature format expected by the saved sklearn pipeline.
3. Call `predict()` and `predict_proba()`.
4. Generate an explanation with `ml/src/explanation.py`.
5. Return the structured response.

The API does not retrain the model, write to the dataset, or call an LLM.

## Disclaimer

This is an AI research prototype prediction based on synthetic data and documented scheme rules. It is not government approval or a final eligibility determination.

## Model loading

The artifact `ml/models/baseline/decision_tree.joblib` is loaded once at application startup. Override the relative path with `MODEL_ARTIFACT_PATH` if needed. Do not point this at a machine-specific hardcoded path in source.

The official catalog `dataset/raw/schemes.csv` is loaded once at startup. Override with `SCHEME_CATALOG_PATH` relative to the project root if needed.

## `GET /api/v1/schemes`

Returns the six CORE schemes that the Decision Tree can score. ADVANCED and HOLD rows stay in `schemes.csv` but are not returned here.

Fields come from the catalog: `scheme_id`, `scheme_name`, `department`, `scheme_category`, `description`, `benefit_description`, `required_documents`, `application_method`, `official_source_url`, `eligibility_notes`, `ml_scope`, `eligibility_rule_status`.

Empty catalog cells are returned as `null`. The literal text `NEEDS VERIFICATION` is returned unchanged.

## `GET /api/v1/catalog`

Additive read-only search over all 13 rows in `schemes.csv`. Independent from `/predict` and `/recommend`. Does not accept client-supplied eligibility results.

Optional query parameters: `q` (name or scheme ID), `ml_scope`, `department`, `gender`, `student`, `category`. `gender=unspecified` and `student=unspecified` match empty catalog cells. Filter values are exact catalog strings; the API does not invent eligibility conditions.

Unfiltered `GET /api/v1/schemes` is unchanged and still returns the six CORE schemes only.

## `POST /api/v1/recommend`

Personalized **eligibility-based** scheme recommendation. The request is a citizen profile only. The API evaluates all six CORE schemes with the same saved Decision Tree used by `/predict`.

This is not behavioral recommendation and not a claim that the model learned real citizen preferences.

### Eligible-only recommendations

`recommendations` contains only schemes whose model prediction is `eligible`. A `not_eligible` scheme is never called recommended.

`evaluated_schemes` lists all six CORE results for research and debugging.

### Ranking logic

1. Keep predicted-eligible schemes only.
2. Sort by `eligible_probability` descending.
3. If probabilities are tied, sort by `scheme_id` ascending.

The Decision Tree often returns 0 or 1 on this synthetic, rule-derived dataset. When every eligible scheme has probability `1.0`, the visible order is the `scheme_id` tie-break. That order is **not** a government priority ranking.

Satisfied-condition counts are not used as a score. For an eligible scheme every documented CORE condition is already satisfied, so a condition count would only measure how many rules that scheme has, which would be an arbitrary score.

### Response fields

| Field | Meaning |
| --- | --- |
| `total_schemes_evaluated` | Always 6 for the current CORE set |
| `eligible_scheme_count` | Number of predicted-eligible schemes |
| `ranking_rule` | `eligible_probability descending, then scheme_id ascending` |
| `recommendations` | Ranked eligible schemes with catalog metadata |
| `evaluated_schemes` | All six CORE predictions and reasons |
| `disclaimer` | Research-prototype disclaimer |

Each recommendation includes `scheme_name`, `description`, `benefit`, `required_documents`, `application_method`, `official_source_url`, model probabilities, and a human-readable `reason` from `ml/src/explanation.py`. `status_label` is `Predicted eligible`. The API never says the citizen is officially eligible.

`official_source_url` is copied from `dataset/raw/schemes.csv`. URLs are not guessed.

## Data wallet endpoints

These routes persist a citizen socio-economic profile in PostgreSQL. They require `Authorization: Bearer <token>`. The backend sets `user_id` from the JWT. The client must not send `user_id`.

If the wallet is missing or belongs to another user, the API returns HTTP 404 so wallets cannot be enumerated.

The create/update body is the same citizen field set as `/recommend`. The server generates `citizen_id`. Eligibility results are never stored.

### `POST /api/v1/auth/register`

Purpose: create a local prototype account. Email is stored lowercased.

Request: `full_name`, `email`, `password` (minimum 8 characters).

Response `201`: `user_id`, `full_name`, `email`. Never includes a password hash.

Errors: `409` email already registered, `422` invalid email or short password, `503` database unavailable.

### `POST /api/v1/auth/login`

Purpose: verify the password hash and issue a JWT.

Request: `email`, `password`.

Response `200`: `access_token`, `token_type=bearer`, `expires_in`, `user`.

Errors: `401` invalid email or password, `422` invalid body, `503` database unavailable.

### `POST /api/v1/auth/google`

Purpose: verify a Google ID token and issue the same application JWT used by email/password login.

Request: `credential` (Google ID token). The backend verifies signature, audience, expiry, issuer, `sub`, and `email_verified`. Frontend-supplied email or name is ignored.

If the verified email already exists, that user is authenticated and `google_sub` is linked when missing. If it does not exist, a local user is created without a password hash.

Response `200`: the same `TokenResponse` as `/login` (`access_token`, `token_type=bearer`, `expires_in`, `user`).

Errors: `401` invalid or unverified Google credential, `422` missing credential, `503` Google Sign-In not configured or database unavailable, `409` rare email conflict.

### `GET /api/v1/auth/me`

Purpose: return the authenticated user. Requires JWT.

Errors: `401` missing, invalid, or expired token.

### `GET /api/v1/wallets/me`

Purpose: return the signed-in user's wallet without asking for `citizen_id`.

Errors: `401`, `404` if the user has no wallet, `503`.

### `POST /api/v1/wallets`

Purpose: create a socio-economic data wallet. The server generates `citizen_id`. Do not send `citizen_id`.

Request: the same citizen fields as `/recommend`.

Response `201`: `citizen_id`, stored fields, `created_at`, `updated_at`. The body never includes eligibility results or the internal database primary key.

Errors: `422` invalid fields, `503` database unavailable, `409` rare generated-ID collision.

### `GET /api/v1/wallets/{citizen_id}`

Purpose: retrieve the saved wallet.

Request: path parameter `citizen_id`. No body.

Response `200`: same shape as create.

Errors: `404` unknown ID, `503` database unavailable.

### `PUT /api/v1/wallets/{citizen_id}`

Purpose: replace the stored socio-economic fields.

Request: path `citizen_id` plus the same citizen body as create.

Response `200`: updated wallet.

Errors: `404`, `422`, `503`.

### `DELETE /api/v1/wallets/{citizen_id}`

Purpose: delete the wallet.

Request: path `citizen_id`. No body.

Response `204` with an empty body.

Errors: `404`, `503`.

### `POST /api/v1/wallets/{citizen_id}/recommend`

Purpose: load the wallet from PostgreSQL and recommend CORE schemes. The client does not send the profile again.

Request: path `citizen_id`. No body.

Response `200`: the same recommendation payload as `POST /api/v1/recommend`.

Errors: `404` unknown wallet, `503` database or model unavailable.

### `GET /api/v1/documents`

Purpose: summarize document preparation progress for CORE schemes that already appear in the caller's recommendation history. GET does not insert checklist rows.

Response `200`: `schemes`, `schemes_with_progress`, `overall_ready_count`, `overall_item_count`, `overall_progress_percent`, and a disclaimer. Progress is checklist completion only. It is not eligibility probability or government approval.

Errors: `401`, `503`.

### `GET /api/v1/documents/schemes/{scheme_id}`

Purpose: return the catalog-backed checklist for one recommended CORE scheme.

If `required_documents` is `NEEDS VERIFICATION` or empty, `documents_need_verification` is `true` and no official document items are invented. A project reminder item is included so the user can record that they reviewed the official source.

Errors: `401`, `404` if the scheme was never recommended to the caller, `503`.

### `PATCH /api/v1/documents/schemes/{scheme_id}/items/{item_key}`

Purpose: save one item status for the JWT owner. Allowed statuses: `not_started`, `ready`, `needs_verification`.

The table stores only `user_id`, `scheme_id`, `item_key`, `status`, and timestamps. Files, Aadhaar numbers, and other identity numbers are not accepted.

Errors: `401`, `404` unknown scheme/item or not in the caller's history, `422` invalid status, `503`.

See `docs/document_checklist_design.md`.

### `GET /api/v1/insights`

Purpose: explain the existing hybrid Rule + ML evaluation of the authenticated user's saved wallet. The documented rule remains the reference when Rule and ML differ.

The route loads the owned wallet and calls `recommend_for_citizen`. It does not save recommendation history and does not change ranking.

Response `200`: `total_schemes_evaluated`, `predicted_eligible_count`, `not_recommended_count`, recommended and other schemes with rule reasons, ML prediction, model probability, agreement, profile completeness, and `Things to Review` codes.

Status labels are `Predicted eligible` and `Not recommended by this prototype`.

Errors: `401`, `404` no wallet, `503`.

See `docs/eligibility_insights_design.md`.

### `GET /api/v1/readiness`

Purpose: summarize manual application-readiness stages for CORE schemes that already appear in the caller's recommendation history. GET does not insert tracker rows.

Response `200`: `schemes`, `schemes_being_prepared`, `overall_progress_percent`, and a disclaimer. Progress is stage-index only. It is not eligibility probability or government approval. Completed Preparation does not mean the government application was submitted or approved.

Errors: `401`, `503`.

### `GET /api/v1/readiness/schemes/{scheme_id}`

Purpose: return the current stage for one recommended CORE scheme.

Errors: `401`, `404` if the scheme was never recommended to the caller, `503`.

### `PATCH /api/v1/readiness/schemes/{scheme_id}`

Purpose: save one stage for the JWT owner. Allowed stages: `not_started`, `profile_ready`, `documents_in_progress`, `ready_to_apply`, `official_source_visited`, `completed_preparation`.

The table stores only `user_id`, `scheme_id`, `stage`, and timestamps. Applications, files, Aadhaar numbers, and payments are not accepted.

Errors: `401`, `404` unknown scheme or not in the caller's history, `422` invalid stage, `503`.

See `docs/application_readiness_design.md`.

### `GET /api/v1/dashboard`

Purpose: aggregate the authenticated user's wallet completeness, recommendation history, document preparation, and application readiness into one progress view. GET does not insert rows and does not score eligibility.

Response `200`: `has_wallet`, `progress`, `journey`, `summary`, `activity`, and a disclaimer. A missing wallet still returns 200 with empty progress. Another user cannot read these rows.

Errors: `401`, `503`.

See `docs/dashboard_progress_design.md`.

### `GET /api/v1/uploads`

Purpose: list optional supporting-document metadata for the JWT owner. Query `scheme_id` may filter to one recommended CORE scheme.

Uploaded files are not verified or officially accepted. Aadhaar, PAN, passport, and biometric documents are not allowed.

Errors: `401`, `503`.

### `POST /api/v1/uploads`

Purpose: store one PDF, JPG, or PNG under 5 MB. Multipart fields: `category`, optional `scheme_id`, and `file`. The server generates the stored filename and checks file magic bytes.

Errors: `401`, `404` if the scheme was never recommended, `422` invalid category/type/name/size, `503`.

### `GET /api/v1/uploads/{upload_id}` and `GET /api/v1/uploads/{upload_id}/file`

Purpose: return metadata or the file bytes for the owner only. Another user receives HTTP 404.

### `PATCH /api/v1/uploads/{upload_id}` and `DELETE /api/v1/uploads/{upload_id}`

Purpose: link/unlink a recommended CORE scheme, or delete the owner's file and metadata.

See `docs/document_upload_design.md`.

### `POST /api/v1/compare`

Purpose: compare 2 or 3 CORE schemes for the authenticated user's saved wallet.

Request: JWT plus `{ "scheme_ids": ["TN-SW-001", "TN-SW-006"] }`.

The backend loads the owned wallet and recomputes hybrid Rule + ML results. Client-supplied eligibility labels are ignored. ADVANCED and HOLD IDs are rejected. Results are not stored.

Response `200`: catalog metadata, `Predicted eligible` or `Not recommended by this prototype`, probabilities, and rule reasons.

Errors: `401`, `404` no wallet, `422` invalid selection, `503`.

### `POST /api/v1/reports/recommendations`

Purpose: generate a recommendation PDF from the caller's wallet. The file is not stored.

Request: JWT plus optional `{ "compare_scheme_ids": ["TN-SW-001", "TN-SW-006"] }`.

Response `200`: `application/pdf` attachment `schemewise-recommendation-report.pdf`.

The PDF never includes passwords, password hashes, or JWTs.

Errors: `401`, `404` no wallet, `422`, `503`.

See `docs/scheme_comparison_design.md` and `docs/pdf_report_design.md`.

## Evaluation APIs

Public, read-only Phase 4/5 research metrics. They do not score wallets, train models, or return user accounts.

Prefix: `/api/v1/evaluation`.

| Path | Source of truth |
| --- | --- |
| `/overview` | `eligibility_dataset.csv` counts plus `run_metadata.json` split |
| `/models` | `run_metadata.json` → `primary_overall` |
| `/schemes` | Dataset eligibility counts; per-scheme ML scores from `docs/model_baseline_results.md` |
| `/features` | CSVs under `ml/models/evaluation/` |
| `/confusion-matrix` | `confusion_matrix_*.csv` |
| `/limitations` | `docs/ml_limitations.md` plus official catalog URLs |

Responses never include passwords, JWTs, user profiles, or wallet rows. Feature importance is an association measure, not a causal claim. Scores measure agreement with the rule engine on synthetic citizens, not government accuracy.

See `docs/evaluation_dashboard_design.md`.

## CORS

Allowed origins remain `http://localhost:5173` and `http://127.0.0.1:5173`. Allowed methods: `GET`, `POST`, `PUT`, `DELETE`, `OPTIONS`. Allowed headers: `Content-Type`, `Authorization`. Credentials are not enabled. `*` is not allowed.
